## Действующий канал GitHub Actions

`backup.yml` запускается ежедневно в 04:15 UTC (08:15 Самара) при `CATS_BACKUP_ENABLED=true`. Канал и постоянный строго ограниченный backup-only ключ установлены; live verify-only и ручной backup прошли. Scheduled runs 15–19 октября успешны; catch-up 20 октября получил архив 19 октября с совпавшим SHA-256. Подтверждённая задержка cron означает, что ранняя локальная задача может взять предыдущий день; сбои 17–18 октября показали только generic status, причина неизвестна. Ошибки видны в результате workflow. Артефакты зашифрованы и запрашивают хранение 30 дней в пределах политики репозитория. Это резервные копии, а не автоматический деплой.

Владелец уже разрешил установку ограниченного пользователя VPS и постоянного **отдельного backup-only** SSH private key в `CATS_BACKUP_SSH_KEY`; запрашивать это согласие повторно не нужно. Общий root/release ключ для backup-доставки не подходит. RSA recovery private key остаётся только у владельца; публичный `backup-recipient.pem` копируется на сервер.

При недоступном локальном SSH подготовлен ручной `backup-bootstrap.yml`. Он допускает только main с успешным Check для точного commit, принимает новый Ed25519 public key как текстовый input, доставляет проверенные исходники во временный каталог VPS и запускает установщик плюс начальную публикацию. Входящий public key передаётся через environment, проверяется до SSH; Private backup key этот workflow не создаёт: получает новый `CATS_BACKUP_SSH_KEY` из secrets и до любых изменений VPS проверяет совпадение его публичной части с согласованным input без вывода значений. Временная файловая копия удаляется при любом исходе. Для этого отдельного, заранее разрешённого запуска нужен временный `CATS_RELEASE_SSH_KEY` с root-доступом; его удаление из repository secrets после согласованных разовых операций выполняется владельцем/агентом отдельно. Workflow удаляет свою временную файловую копию ключа при любом исходе. Bootstrap не включает расписание и не выполняет deployment приложения. После установки workflow новым ограниченным ключом скачивает один свежий encrypted envelope и проверяет реальный отказ id/bash/SCP-команды, SFTP subsystem, PTY и remote forwarding. SFTP-отказ подтверждается настоящим INIT v3 и SSH verbose-свидетельствами аутентификации, принятия subsystem и exit 1; сетевые, auth и timeout ошибки отказом канала не считаются. Неуспешные проверки доступа оставляют расписание отключённым; уже завершённая транзакция установки при этом сохраняется для диагностики. Если установка, начальная публикация, проверка sshd или reload неуспешны, установщик откатывает только созданные им точные файлы, новые пустые каталоги и нового пользователя/группу; восстанавливает конфигурацию сервисов без удаления прежних файлов. Расписание остаётся отключённым. Уже существующая конфигурация отклоняется до изменений.

Установщик принимает файл с одним Ed25519 **публичным** ключом; процедура ниже описывает установку канала и приведена как операционная справка: текущий live proof уже прошёл.

```sh
sudo bash ops/backup-channel-install.sh /absolute/path/new-backup-key.pub
```

Установщик требует существующий root backup-service, `/usr/bin/node`, gzip и GNU tar, поддержку sshd drop-in Include. Он отказывается изменять уже существующего `cats-backup`, группу или свои каталоги/конфиги. При несовпадении предпосылок нужна проверка фактической конфигурации VPS, а не обход отказа. Скрипт не генерирует ключи и не обращается к GitHub. Исходный backup-service сохраняется: добавляется только `ExecStartPost`, который после успешного backup публикует encrypted envelope. Начальная публикация свежего существующего архива выполняется внутри транзакции установщика до успешного reload; backup-service во время установки не запускается. Файлы модуля и публичный ключ устанавливаются root в `/usr/local/lib/cats-backup`, вне изменяемого каталога проекта.

Пользователь `cats-backup` читает только root-owned `/var/lib/cats-backup-export/latest.enc`. Forced command принимает ровно `export-latest`; shell, SCP/SFTP, PTY и forwarding запрещены. Исходные архивы с секретами ему не выдаются. Имя, возраст до 36 часов, размер до 512 MiB, отсутствие symlink, целостность gzip/tar и SHA-256 проверяются перед шифрованием. Неуспешная публикация сохраняет предыдущий envelope, который перестаёт экспортироваться после истечения свежести. На GitHub проверяются формат/свежесть и границы размера; криптографическая проверка AES-GCM выполняется при локальном расшифровании существующим `backup-envelope.mjs`.

Перед включением `CATS_BACKUP_ENABLED` требовалась проверка новым ограниченным ключом; эта проверка пройдена run `38586022324`: `export-latest` выдаёт envelope; `id`, `bash`, SCP/SFTP и PTY/forwarding отвергаются. Затем ручной workflow должен скачать только `.enc`, который локально расшифровывается с совпадением SHA-256. После этого проверяется первый успешный ежедневный запуск. Настройка расписания сама по себе не подтверждает своевременность копии текущего дня.

Локальные проверки, без серверов и постоянных ключей:

```sh
node ops/backup-channel-test.mjs
node ops/backup-installer-test.mjs
bash -n ops/backup-channel-install.sh ops/backup-export.sh
```

Тест использует одноразовый RSA fixture во временной папке: проверяет roundtrip, отказы команд, свежесть, повреждённый gzip и сохранение предыдущей копии. Symlink fixtures выполняются на POSIX; Windows пропускает их из-за ограничений создания symlink. На Windows тест добавляет gzip/GNU tar из Git for Windows только в собственный PATH. Installer fixtures запускаются в изолированных временных каталогах с подставными административными командами и проверяют откат при отказах sshd, эффективной политики, публикации и reload; реальные системные файлы и пользователи не меняются. Реальные права SSH/systemd подтверждаются только при отдельно разрешённой установке. Отключение канала: установить `CATS_BACKUP_ENABLED=false`; удаление пользователя/ключа на VPS требует отдельной явной операции администратора.
